# 自作 macOS IME「RomKana」開発記（続）— 文節変換と個人最適化

[前回の開発記](https://zenn.dev/toshinao/articles/1cffb713b1c670)では、ローマ字をローカルでかな漢字に変換する macOS の IME を、辞書＋ローカルLLM（第1部）から **AzooKeyKanaKanjiConverter ＋ Zenzai**（第2部）へ作り直すところまで書きました。毎日使える道具にはなったのですが、使い込むと「もっとこうしたい」が2つ出てきました。

- **(a) 空白で区切らずに長文を打つと、一部分だけを直せない。**
- **(b) 社内用語や固有名詞を、その都度ユーザー辞書に手で足している。**

この2つを潰した記録です。現行構成のリファレンスは [`architecture.md`](https://github.com/t10471/RomKana/blob/master/docs/architecture.md) を参照してください。

---

## 1. 文節変換 — 空白なしでも一部だけ選び直す

前回（第2部・11章）で「空白で区切る＝文節境界を教えてもらって、1語だけ差し替える」はできていました。でも空白なしで長文を一発変換したとき、途中の1文節だけ間違っていると、文全体の別候補から選び直すしかありません。標準的な日本語IMEのように「**←/→ で文節を選び、その文節だけ変換し直す**」をやりたくなりました。

AzooKey の中を調べてみると、**文節分割の出し方が一筋縄ではない**と分かりました。

- ❌ 最初は `firstClauseResults`（先頭文節の候補）を取り、`prefixComplete` で前から1文節ずつ切り出す方式にしました。きれいに分かれる…はずが、「きょうははいしゃにいく」が**まるごと1文節「今日は歯医者に行く」**になってしまうことがある。これだと → を押しても動きません（そもそも分かれていない）。
- ✅ そこで、文全体のベスト候補の**構成要素（単語列）**で区切る方式に変えました。各単語がカバーする読みの文字数で、読みをスライスして文節にする。これなら複数語の文は必ず複数文節に分かれます。

🔑 もう一つ、AzooKey には**「文節の境界を伸び縮みさせる API」が無い**ことも分かりました。変換は常に文全体に対して走ります。なので、文全体の読みを自前で「文節ごとの区切り位置」として持ち、境界を動かしたら**影響する文節だけ読みを再変換する**形にしました。第2部で作った空白チャンク変換の仕組みが、ほぼそのまま流用できたのは助かりました。

### ターミナルでフォーカスが見えない

動くようになって喜んだのも束の間、**WezTerm で使うとどの文節を選んでいるか分からない**。調べると、macOS では WezTerm の preedit 描画設定が効かず、こちらが付けた文節区切り（`markedClauseSegment`）・背景色・下線の太さを**ターミナルは反映しない**のでした（GUIアプリなら出ます）。割り切って、フォーカス文節を `《…》` で囲んで表示することにしました。端末でもはっきり分かりますし、確定する文字に記号は入りません。

### 「→を押すと消える」の正体

使ってみると「最後まで打って → を押すと全部消える」という現象が出ました。ログを仕込んで再現したら、**押していたのは Shift+→ でした**。Shift+Space で変換した直後、Shift を押したまま → を押すと、当時 Shift+←/→ に割り当てていた「境界伸縮」が暴発していました。先頭文節が隣をどんどん吸収して、最後は1文節に統合されます。消えていたのではなく、まとまっていたのです。なので **フォーカス移動は ←/→（Shift の有無に関係なく）**、**境界伸縮は Option+←/→** に変えました。変換キー（Shift+Space）の修飾が指に残っても誤爆しません。地味ですが、「変換キーと編集キーの修飾がぶつからないように割り当てる」のは大事だと学びました。

### 「聞いて返ってきた」が「帰って」にしかならない

毎日使っていると、自分がいちばんのテスターになります。空白なしで `きいてかえってきたもの` と打つと、`かえって` を `返って` に選び直せない、と気づきました。掘ってみると原因が3つ重なっていました。

- **文節の境界がずれる。** ベスト候補の構成要素で区切る方式だと、`聞いて帰ってき` のように **te形の連なりが1要素に癒着**して、`かえって` が独立した文節になりません。`firstClauseResults` で切り直そうとしても、今度はこの節の冒頭で書いた「まるごと1文節」の崩壊が起きます。
- **Zenzai が同音異字を落とす。** `かえってきた` 単体を変換しても、Zenzai は「入力全体をカバーする候補」に `返ってきた` を残しません。ところが **Zenzai を切った辞書ラティス単体なら `返ってきた` が候補に出ます**。
- **しかも出たり出なかったり。** 最初の直しでは「癒着しているか」を Zenzai のベスト候補で判定していたのですが、Zenzai はサンプリングで毎回わずかに違う答えを返すので、**同じ入力でも分割が変わる**気持ち悪い挙動になりました。

直し方はこうです。**癒着の判定は、毎回同じ答えになる辞書ラティス（Zenzai オフ）で行う**。再分割は、**漢字のかたまりがちょうど1つになる「いちばん長い前方」で切る**（`聞いて帰って` は漢字が2つ＝2文節なので却下し、`聞いて` で切る）。そして文節ごとの候補は **Zenzai あり・なしの両方をマージ**して、Zenzai が落とした `返ってきた` も選べるようにしました。正常な文はこれまでどおり Zenzai の文脈変換に任せ、癒着を検出したときだけ再分割します。

### 逆に「切りすぎ」でも選べない — 範囲は自分で決める

かえって（まとめすぎ）を直したら、鏡写しの問題が出ました。`はいか` は `は｜いか`（助詞の「は」＋「いか」）と**切られすぎて**、`配下`（全体で1語）が文節をまたいで選べません。候補一覧には `配下` があるのに、分割が邪魔をする。自動の文節分割は、**まとめすぎでも切りすぎでも**狙った語に届かず、しかも文脈しだいで正解が変わります。機械の推測だけで両取りするのは無理でした。

そこで、**範囲は使う人が決められる**ようにしました。変換後に **Shift+Space を押すと、フォーカス中の文節が1かなずつ縮み、いちばん短くなったら全体に戻って循環**します（`は` → `はいか` → `はい` → `は` …）。切られすぎても Shift+Space でまとめ直して `配下` を出せます。第1部の「賢いのは使う人の癖」と同じで、境界も最後は人が決めるのがいちばん確実でした。

範囲調整は最初 Option+←/→（前節で Shift+←/→ から移した、あれ）に載せていたのですが、**WezTerm では効きませんでした**。ログを見ると、Option+→ を押しても IME に届くのは修飾なしの矢印だけ（`option=false`）。ターミナルは Option を Alt/Meta として自分で使うので、修飾キーを入力メソッドに渡してくれないのでした（GUIアプリなら届きます）。なので、確実に IME まで届く **Shift+Space** に範囲変更を寄せました。marked text に続く、また端末の話です。

### 「たまに入力が消える」の犯人

「変換中にときどき入力が消える」という報告も出ました。ログで追うと、**空白区切りで変換したときのフラットな候補一覧**で ←/→ を押すと、その矢印がどの分岐にも当たらず「現在候補を確定して、矢印を下のアプリに素通しする」経路に落ちていました。候補を見ながら何気なく矢印を押すと、**①勝手に確定 ②矢印がターミナルのTUIに抜けてカーソルが動く**、が同時に起きて「消えた」ように見えていたのです。←/→ を候補移動に割り当てて塞ぎました。キーは「効かせる」だけでなく、**未処理のキーをうっかり確定に落とさない**のも設計のうちでした。

### 「消える」には続きがあった — 今度は本当に落ちていた

矢印の件で片付いたと思ったら、まだ消えます。しかも今度は様子が違う。候補を選ぶ前、変換した瞬間に打っていた文字が**まるごと消える**。矢印の素通しでは説明がつきません。

キーごとに mode と buffer を吐くログを仕込んで見ると、変な点に気づきました。「変換した（CONVERT）」の直後、次のキーではもう mode が composing に戻り、buffer は空。なのに確定（COMMIT）も取り消し（RESET）も記録が無い。**確定も取り消しもしていないのに、状態だけ初期値に戻っている**。正常な流れではあり得ません。

心当たりは1つ。プロセスが落ちれば状態は初期値に戻り、ログもそこで切れる。`~/Library/Logs/DiagnosticReports/` を見たら、案の定 **RomKana のクラッシュレポートが並んでいました**（その日だけで数回）。スタックはこうでした。

```
Swift runtime failure: Index out of range
  ...
  Kana2Kanji.kana2lattice_afterComplete(…)   ← AzooKey 内部
  KanaKanjiConverter.requestCandidates(…)
  RomKanaController.firstClauseLen(…)         ← こちらの文節分割
  RomKanaController.startConversion(…)
```

配列の範囲外アクセスで **SIGTRAP、プロセスごと即死**。プリエディットはプロセスと一緒に消えていました。「入力が消える」は比喩でも表示バグでもなく、**文字どおり落ちていた**のです。

原因は、こちらの使い方と AzooKey の想定のズレでした。確定のたびに `setCompletedData` を呼んで「直前の文脈」を渡していたのですが、これが使う `afterComplete` は、**文節を1つ確定して残り（＝前の入力の末尾）を続けて変換する**逐次確定用の経路です。確定済みの文字数ぶん前方をずらして計算します。ところが RomKana は**文を一括で確定**する作りなので、この前提が成り立ちません。さらに前の節で入れた「切りすぎを直す文節分割」が読みの**末尾部分**を何度も変換し直すため、AzooKey の「これは前の入力の末尾か?」という判定にたまたま一致してしまう。そこへ古い文脈が残っていると、確定文字数（`が`＝1）と実際にずらすべき長さ（`にゅーりょくが`＝6）が食い違い、ラティスの添字が範囲外へ飛んで落ちる、という筋でした。

直しは拍子抜けするほど単純で、**`setCompletedData` を呼ぶのをやめました**。学習は別系統（`updateLearningData`）が担うので、賢さは何も失いません。文脈を渡さなければ、落ちる経路にはそもそも入らない。便利そうだからと足したAPIが、設計と前提が合わずに牙をむいた一件でした。

### 結局 ATOK 風のキーに落ち着いた

ここまでの節を読み返すと、キーの割り当てでずっと綱引きをしていました。

- 変換は Shift+Space。でもその Shift が指に残ると、Shift+←/→ の文節伸縮が暴発する。→ 伸縮を Option+←/→ に逃がした。
- ところが Option+←/→ はターミナルに届かない（IME に渡らない）。→ 苦しまぎれに Shift+Space へ「範囲の循環」を足した。

工夫を積むほど、標準の日本語IMEとは似ても似つかない操作になっていきます。腰を据えて考えると、**元をたどれば「変換を Shift+Space に置いた」のが全部の発端**でした。Shift を変換に取られているから、編集で Shift が使えない。

そこで変換を Shift から切り離しました。ATOK と同じく **変換は Tab**。すると Shift が空くので、文節の伸縮を **Shift+←/→**（これも ATOK 風）に戻せます。しかも Shift+←/→ はターミナルにも届く。Shift+Space の暴発も、Option がターミナルで死ぬ問題も、両方いっぺんに消えました。

Tab に移して初めて見つかった穴もありました。**2回目の Tab で全文が確定してしまう**。文節モードで Tab が「未処理キー」扱いになり、既定の「確定して下のアプリへ素通し」に落ちていたのです。変換キーを続けて押したら次候補へ送る、という当たり前を実装して塞ぎました。

修飾キーがぶつかり続けたとき効いたのは、**別の修飾を足すことではなく、大元の変換キーを中立な場所（Tab）へ動かすこと**でした。回り道をした分、痛感しました。

## 2. 個人最適化 — 自分の語彙に寄せる

社内用語や固有名詞（社内の略語や製品名など）を、その都度ユーザー辞書に手登録していました。これを「使っているうちに勝手に賢くなる」形にできないか。

調べてみると、**AzooKey/Zenzai には個人最適化の仕組みが最初から入っていました**。`convertOptions` で `personalizationMode: nil` にしていた、まさにそこです。仕組みは、自分の文章から作った**個人 N-gram モデル**を、汎用の **base N-gram** で割った比（＝自分はよく使うが世間では珍しい言い回し）で、Zenzai の候補を持ち上げる、というもの。本家の [azooKey-Desktop](https://github.com/azooKey/azooKey-Desktop) も同じ仕組み（Tuner）で個人最適化しています。

実装で1つ制約にぶつかりました。**学習関数（`trainNGram`）を持つモジュールが外部公開されていない**のです。推論側（個人モデルを使う）は `personalizationMode` にファイルのパスを渡すだけで動く（変換器が中で読んでくれる）のに、学習だけは本体から直接呼べない。なので学習は、AzooKey の CLI ツールを `swift run` で別プロセスとして回す**スクリプト**に分けました。流れはこうです。

1. 確定した文を履歴ファイルに貯める（個人最適化を ON にしたときだけ・平文ローカル）。
2. ある程度貯まったら、スクリプトで個人 N-gram モデルを学習する。
3. base モデル（[Hugging Face にある n=5 の汎用 N-gram](https://huggingface.co/Miwa-Keita/base_n5_lm)）と合わせて有効化する。

N-gram なので軽い（数十MB）し、本体モデルを再学習するのと違って**汎用の変換性能を壊すリスクが無い**（混ぜる強さを `alpha` で調整できる）のが気に入っています。前回の第1部で「賢いのはモデルより使う人の癖」と書きましたが、その癖を今度は N-gram という形で素直にモデルへ取り込めるようになった、という感覚です。

正直なところ、効果がはっきり出るには履歴がそれなりに要りますし、base モデルが HF にライセンス明記が無い（なので個人利用に留め、リポジトリには含めず取得手順だけ置いた）といった注意点もあります。まだ育て始めたばかりです。

### 実際に回してみたら、履歴の8割が断片だった

「育て始めたばかり」と書いたので、一度きちんと回してみました。まず引っかかったのが**鶏と卵**です。個人最適化が効くのは base と個人モデルが両方そろったときだけ。個人モデルには履歴が要る。その履歴は ON の間しか記録されない。だから「ON にする → しばらく使って貯める → 学習する → 有効化」の順にしか進めません。

しばらく使うと履歴が約2,800行たまりました。ところが中身を見て驚きます。**8割が5文字以下**。`で` `を` `。` `調べて` といった助詞や単独の文節ばかりでした。原因は自分の使い方です。文節ごとにこまめに確定するので、1行が1文にならず、細切れで貯まっていました。

文字のつながりを学ぶ N-gram に断片を食わせても実りは薄い。そこで**6文字以上の行だけ**に絞り、8割を捨てて約600行を残しました。`間違っている気がする` `わかりにくい` のような、まともなフレーズです。学習し直すと、ログが `PERSONALIZATION off (model missing)` から `PERSONALIZATION on` に変わりました。効果はまだ地味ですが、パイプラインは動くし、使うほど履歴は増えます。学びは1つ。**自分で集める学習データの質は、道具の使い方の癖がそのまま出る**。データは「量」より先に「どう集まるか」を見ておくべきでした。

## 今回の教訓

- **ライブラリは公開APIの境界で設計が決まる。** 個人最適化は推論こそパスを渡すだけで有効化できたのに、学習関数は非公開で、CLI を別プロセスで回す形に分けることになりました。「使えると思った機能が、半分しか公開されていない」のはよくある話で、境界を最初に確かめるべきでした。
- **自分で集める学習データは、使い方の癖がそのまま質になる。** 個人最適化の履歴は、文節ごとにこまめに確定する癖のせいで8割が断片でした。6文字以上に絞って学習。データは「量」だけでなく「どう集まるか」まで見ておくべきでした。
- **ターミナルとGUIで marked text の扱いが違う。** 文節のフォーカスは属性（下線・背景・clause segment）で見せるとGUIでは出るが端末では消える。記号（`《》`）で囲むのが結局いちばん確実でした。
- **修飾がぶつかり続けたら、別の修飾でなく大元のキーを動かす。** Shift+Space 変換の Shift が矢印に残って伸縮が暴発 → Option+←/→ に逃がすと今度は端末で届かない、と堂々巡り。最後は変換を Tab に移して Shift を編集用に空け、フォーカス移動は ←/→、伸縮は Shift+←/→（ATOK風・端末でも効く）に落ち着きました。
- **設計の判断材料にする出力は、決定的かどうかを確かめる。** 文節が癒着しているかの判定を Zenzai（サンプリングあり）の結果でやったら、同じ入力で分割が揺れました。判定を辞書ラティス（毎回同じ答え）に寄せたら安定しました。賢い出力ほど、揺れることを忘れがちです。
- **自動分割は両取りできない。** まとめすぎ（かえって）と切りすぎ（はいか）が両方起き、文脈しだいで正解も変わる。最後は「範囲を人が選べる」ようにするのがいちばん確実でした（Shift+←/→ で文節の区切りを手で伸縮）。
- **便利なキーも、環境によっては届かない。** 文節伸縮を Option+←/→ にしたら、WezTerm は Option を IME に渡さず不発。GUIでは動くだけに気づきにくい罠です。最終的に、端末にも届く Shift+←/→ に寄せました（変換を Tab に逃がして Shift を空けたのが効いた）。
- **キーは「効かせない」設計も要る。** フラットな候補一覧で未処理の ←/→ が「確定＋アプリへ素通し」に落ち、入力が消えて見えました。矢印も候補移動に割り当てて塞ぎました。
- **「入力が消える」は、プロセスが落ちているのかもしれない。** 確定も取り消しもしていないのに状態が初期化されていたら、まずクラッシュを疑う。決め手は `~/Library/Logs/DiagnosticReports/` のレポートとスタックでした。ライブラリのAPIも、自分の設計と前提が合っていなければ範囲外で落ちます（一括確定なのに逐次確定用の `setCompletedData` を渡していた）。
- **再インストールでフォールバックIMEが湧く。** バンドルを消して作り直すと、macOS が一瞬 RomKana を見失って ATOK など他の日本語IMEを有効化してしまう。バンドルは消さず、中のバイナリだけ差し替えて再起動する形にしました。第1部の「難しいのは変換より OS への登録」の続きです。
- **「賢いのは使う人の癖」は今も同じ。** 第1部ではユーザーの選択履歴で同音語を分岐させ、今回はその癖を個人 N-gram としてモデルに渡す。アプローチは変わっても、効くのは結局「その人のデータ」でした。
